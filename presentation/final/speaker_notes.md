## Slide 3: 1B 모델은 4GB에 들어갔다—그래서 질문을 바꿨다 (0:45)

목표 시간: 0:45

기억할 문장: Gemma 3 1B는 용량 모델상 K26 4GB에 들어가므로 외부 8GB는 필수가 아닙니다.

발화문: 처음에는 외부 8GB가 단순히 모델을 담기 위해 필요하다고 생각했습니다. 그런데 실제 용량을 계산해 보니 Gemma 3 1B는 K26의 4GB 안에도 들어갔습니다. 그래서 질문을 바꿨습니다. 외부 메모리는 더 큰 창고이기만 해서는 의미가 없고, 가중치 공급을 분리해 얻는 이득이 운반 비용보다 커야 합니다. 외부 8GB는 3B 이하 확장과 공급 경로 분리를 평가하기 위한 구조입니다.

그림 설명 순서: 처음 가설 → 2.43 GiB → 의사결정식 → 새 질문

전환: 이 질문을 두 장치의 역할 분리로 구체화했습니다.

예상 질문: 1B가 4GB에 들어가는데 왜 외부 8GB인가?

20초 답변: 1B 필수 용량이 아니라 공급 분리와 더 큰 모델·긴 문맥 확장 조건을 평가하기 위해서입니다.

근거 파일: results/model_level/k26_local_external_sensitivity.csv

해석 경계: 2.43 GiB는 INT8·문맥 32K·실행 여유의 용량 모델이며 보드 실측이 아닙니다.

주의할 표현: 외부 8GB가 Gemma 1B의 필수 용량이라고 말하지 않는다.

## Slide 4: 계산과 가중치 공급을 두 장치로 분리했다 (0:50)

목표 시간: 0:50

기억할 문장: K26의 계산 위치와 Memory FPGA의 데이터 위치를 연산 타일에서 함께 추적합니다.

발화문: K26은 운영체제와 제어, 네 연산 클러스터, 로컬 대기열, MatVec를 맡습니다. Memory FPGA는 가중치 저장과 네 메모리 채널, 채널 선택, 링크 전송을 맡습니다. 연산 타일, 즉 TileJob은 계산할 클러스터와 가중치가 가까운 채널을 함께 기록합니다. 실선은 현재 RTL이나 모델에 존재하는 경로이고, 점선은 아직 남은 실제 직렬 링크와 메모리 제어 경로입니다.

그림 설명 순서: K26 역할 → 요청 경로 → Memory FPGA 역할 → 응답 경로 → 선 경계

전환: 이 구조가 기존 접근과 어떻게 다른지 비교하겠습니다.

예상 질문: 왜 K26과 Memory FPGA의 역할을 분리했는가?

20초 답변: K26은 계산 소유권을, Memory FPGA는 데이터 위치와 다채널 공급을 담당하게 해 두 비용을 분리합니다.

근거 파일: docs/architecture.md · ClosedLoopVirtualPrototypeTop.scala

해석 경계: 논리 경로 일부는 RTL에 있으나 실제 GTH·CDC·MIG 물리 경로는 닫히지 않았습니다.

주의할 표현: 실선을 전체 물리 경로 구현으로 확대하지 않는다.

## Slide 5: 메모리 용량만 늘리지 않고 작업 배치와 데이터 위치를 함께 설계했다 (0:35)

목표 시간: 0:35

기억할 문장: 독창성은 Work Stealing 자체가 아니라 실제 모델·초기 배치·이동 비용·물리 인터페이스를 한 설계 흐름에서 연결한 점입니다.

발화문: 기존 연구는 연산량이나 대역폭, 정적 배정, 합성 행렬, 또는 개별 RTL 구현에 집중하는 경우가 많았습니다. 이 연구는 연산·메모리·링크의 균형을 함께 보고, 이동 비용을 고려해 작업을 선택적으로 재분배하며, 실제 Gemma 그래프에서 작업을 추출해 모델에서 RTL과 PCB 참조 설계까지 연결했습니다. Work Stealing은 기존 기술이며, 여기서는 구조 채택 조건을 찾는 도구입니다. 관련 연구 비교 기준은 FTRANS의 대형 모델 전송, DFX의 분산 FPGA 실행, FlightLLM의 메모리 중심 가속, 고전적 Work Stealing의 부하 균형, LAWS의 지역성 고려입니다. 화면은 문헌에 명시된 범위만 요약합니다.

그림 설명 순서: 기존 접근 → 본 연구 → 하단 연구 핵심

전환: 이제 직접 검증한 MatVec 범위를 보겠습니다.

예상 질문: Work Stealing은 기존 기술인데 무엇이 새로운가?

20초 답변: 알고리즘 신규성이 아니라 실제 Gemma 형상·초기 배치·원격 비용·RTL·PCB를 하나의 채택 분석으로 연결한 점입니다.

근거 파일: 논문 II장 · 문헌 [6–8, 15–16]

해석 경계: FTRANS·DFX·FlightLLM·고전적 Work Stealing·LAWS와 논문에 적힌 비교 항목만 사용합니다.

주의할 표현: Work Stealing 자체를 알고리즘 독창성으로 주장하지 않는다.

## Slide 6: 실제 Gemma 가중치를 MatVec RTL에서 검증했다 (0:35)

목표 시간: 0:35

기억할 문장: 직접 증명한 것은 실제 Gemma 가중치 세 타일의 16×4 INT8 MatVec 산술 일치입니다.

발화문: 실제 Gemma 가중치를 추출해 시험 입력을 만들고, 16×4 INT8 MatVec RTL에 넣은 뒤 소프트웨어 INT32 기준값과 비교했습니다. gate projection, lm_head, output projection 세 타일이 모두 정확히 일치했습니다. 이 시험은 MatVec 산술을 확인한 범위이며 실제 DDR 읽기나 FPGA 간 링크 성능은 포함하지 않습니다.

그림 설명 순서: 실제 가중치 → 시험 입력 → MatVec RTL → 기준값 비교 → 3/3

전환: 정확한 산술만으로는 정적 배정의 유휴 문제를 해결할 수 없습니다.

예상 질문: 실제 FPGA 성능을 측정했는가?

20초 답변: 아닙니다. 실제 가중치 세 타일의 MatVec RTL 일치만 직접 확인했고 성능은 분석 모델입니다.

근거 파일: evidence/model/gemma3_1b_rtl_tile_parity.csv

해석 경계: 응답 데이터는 시험 경계에서 주입했으며 전체 Gemma 추론·실제 DDR·물리 링크는 검증하지 않았습니다.

주의할 표현: 3/3 일치를 전체 모델 실행·성능으로 확대하지 않는다.

## Slide 7: 정적 배정은 데이터를 가까이 두지만 작업을 고르게 나누지 못한다 (0:30)

목표 시간: 0:30

기억할 문장: 정적 로컬 큐는 가중치 이동을 줄이지만 작업 쏠림을 스스로 고치지 못합니다.

발화문: 정적 로컬 큐, S1은 각 작업대 앞에 고정된 대기 줄을 둔 것과 같습니다. 가중치를 가까이 둘 수 있지만 C0에 일이 몰리면 C2와 C3가 비어 있어도 돕지 못합니다. 그래서 평균보다 마지막 작업과 p95·p99 꼬리 지연이 길어질 수 있습니다.

그림 설명 순서: C0 집중 → C2·C3 유휴 → 장점과 한계

전환: 빈 작업대가 이득이 있는 일만 가져오도록 바꿨습니다.

예상 질문: 왜 중앙 큐가 아니라 로컬 큐인가?

20초 답변: 로컬 큐는 가중치 지역성과 분산 제어를 유지하면서 정적 배정의 불균형을 관찰하기 위한 기준선입니다.

근거 파일: 정적 로컬 큐 개념 · 수치는 Slide 11

해석 경계: 화면의 큐는 개념도이며 성능 수치는 뒤의 분석 모델에서 제시합니다.

주의할 표현: 정적 로컬 큐가 모든 조건에서 나쁘다고 일반화하지 않는다.

## Slide 8: 빈 연산기가 이득이 있는 작업만 가져온다 (0:40)

목표 시간: 0:40

기억할 문장: 지역성 인식 작업 재분배는 대기 감소가 운반 비용보다 클 때만 동작합니다.

발화문: 지역성 인식 작업 재분배, S3는 빈 작업대가 옆 줄의 일을 가져오는 방식입니다. 먼저 유휴 연산기를 찾고, 가져올 수 있는 작업의 기다림 감소와 가중치·활성값 이동 비용을 비교합니다. 이득이 더 클 때만 소유권을 옮깁니다. 따라서 Work Stealing은 연구의 목적이 아니라 제한된 자원을 쓰기 위한 선택 수단입니다.

그림 설명 순서: 유휴 발견 → 이득·비용 비교 → 조건부 이전 → 부등식

전환: 이 정책을 실제 Gemma 작업 단위로 바꾸겠습니다.

예상 질문: 어떤 조건이면 작업을 옮기지 않는가?

20초 답변: 대기 감소가 가중치·활성값 이동 비용보다 작거나 작업이 옮길 수 없으면 재분배하지 않습니다.

근거 파일: src/varp/k26_scheduler_model.py

해석 경계: 정책 영상은 상태 전이를 설명하며 최적성 증명이나 실제 보드 타이밍이 아닙니다.

주의할 표현: 정책 점수를 최적성 증명이나 보드 타이밍으로 말하지 않는다.

## Slide 9: Gemma 그래프를 802개 연산 타일로 나누고 단계 의존 규칙을 부여했다 (0:35)

목표 시간: 0:35

기억할 문장: 실제 모델의 7,837개 노드에서 183개 투영을 찾고 802개 연산 타일로 분할했습니다.

발화문: 실제 Gemma ONNX 그래프의 7,837개 노드에서 토큰당 183개 행렬 투영 연산을 찾았습니다. 큰 행렬 하나를 여러 출력 타일로 나누면 802개 연산 타일이 됩니다. 질의·키·값 다음 출력 투영, 게이트·상향 다음 하향, 그다음 계층이라는 보수적 단계 의존 규칙을 부여했습니다. 32토큰에서는 25,664개입니다.

그림 설명 순서: 7,837 → 183 → 802 → 분할 이유 → 의존 순서

전환: 이제 같은 작업에서 정책만 바꾼 대표 사례를 보겠습니다.

예상 질문: 183개 투영과 802개 연산 타일은 무엇이 다른가?

20초 답변: 183은 그래프 연산 수이고 802는 큰 행렬을 출력 방향으로 나눈 하드웨어 작업 수입니다.

근거 파일: projection_trace.csv · gemma3_1b_dependency_manifest.json

해석 경계: 802와 25,664는 고정한 그래프 형상과 명시한 타일 분할·보수적 단계 규칙에서 나온 모델링 수치입니다.

주의할 표현: 그래프 기반 작업 수를 실제 FPGA 실행 횟수로 부르지 않는다.

## Slide 10: 같은 작업에서 정적 배정과 작업 재분배만 비교했다 (0:45)

목표 시간: 0:45

## Slide 11: 작업이 치우친 경우에만 재분배가 효과적이었다 (0:45)

목표 시간: 0:45

기억할 문장: 재분배 효과는 부하 불균형과 초기 데이터 배치에 조건부입니다.

발화문: 합성 불균형 부하에서는 정적 배정보다 p95가 19.13%, p99가 18.71% 줄었습니다. 하지만 Gemma 형상에서는 기존 초기 배치가 p95를 0.28% 늘렸고, 메모리 채널을 고려한 초기 배치에서는 19.79% 줄였습니다. 즉 스케줄링만 따로 떼어 항상 좋다고 말할 수 없고, 처음 데이터를 어디에 놓았는지와 함께 봐야 합니다.

그림 설명 순서: 합성 불균형 → Gemma 기존 배치 → 채널 고려 배치 → 조건 문장

전환: 꼬리 지연을 줄인 대가가 무엇인지 이어서 보겠습니다.

예상 질문: 왜 어떤 조건에서는 재분배가 더 느린가?

근거 파일: paired_policy_effects.csv · gemma3_1b_policy_effects.csv

해석 경계: p95·p99는 의존성 해제 뒤 연산 타일 완료 분포이며 사용자 요청 지연이 아닙니다.

주의할 표현: 연산 타일 p95를 사용자 요청 지연으로 부르지 않는다.

## Slide 12: 유휴 연산은 줄었지만 데이터 이동이 새로운 비용이 됐다 (0:40)

목표 시간: 0:40

기억할 문장: 지역성 점수는 무제약 재분배보다 원격 가중치를 줄이지만 완료시간은 조금 늘 수 있습니다.

발화문: 정적 배정과 비교하면 지역성 인식 재분배의 p95는 19.13% 줄었습니다. 반면 무제약 재분배와 비교하면 원격 가중치는 35.49% 줄었지만 마지막 완료시간은 0.01% 늘었습니다. 앞의 수치는 정적 배정 대비 효과이고 뒤의 두 수치는 재분배 방식끼리의 비교입니다. 서로 다른 기준이므로 하나의 인과효과처럼 연결하지 않습니다.

그림 설명 순서: 정적 배정 대비 → 무제약 재분배 대비 → 기준 차이

전환: 이 비용까지 포함해 외부 메모리 채택 조건을 보겠습니다.

예상 질문: 세 수치의 비교 기준이 왜 다른가?

20초 답변: 정적 배정 효과와 무제약 재분배 대비 지역성 효과를 분리하기 위한 서로 다른 기준입니다.

근거 파일: results/experiments/paired_policy_effects.csv

해석 경계: 분석 모델의 비교 기준이 다르며 서비스 중첩 가정에 따라 정책 순위가 바뀔 수 있습니다.

주의할 표현: 서로 다른 기준 수치를 하나의 인과식으로 묶지 않는다.

## Slide 13: 현재 모델 가정에서는 K26 로컬 경로가 유리했다 (0:50)

목표 시간: 0:50
